# تسليم MVP 0.2.0 — نتائج فعلية وحدود معلنة

تم تنفيذ المراحل 3–7 وظيفيًا في النطاق المضيق الموثق بقرار المحرك: حفظ الأصل، قراءة، تصنيف وحقول، مراجعات مستقلة، بحث، API، واجهة عربية، وتثبيت ونسخ واستعادة محلية. **لم تكتمل مقارنة محركي OCR الأصلية**؛ نطاق Paddle محجوب وأوزانه غير محققة الترخيص أو البصمة بعد. لذلك OCR مساعد إلزامي المراجعة ولا يعتمد تلقائيًا، ولا توجد دعوى تفوق محرك أو جاهزية حكومية إنتاجية.

## المرحلة الثالثة: المعالجة والحفظ

المدخلات ملفات PDF/PNG/JPEG ضمن الحدود. المخرجات أصل محفوظ ببصمة، Document، Page لكل صفحة، وProcessingRun مستقل لكل محاولة. duplicate لا يعيد المعالجة؛ retry يحتفظ بنتائج السابق. اكتشاف الفشل والتشفير وحدود الصفحات والبكسلات لا يسجل نجاحًا. يعود التشغيل من المحاولات المنقطعة إلى failed، ويستعيد سجل أصل وضع قبل انقطاع تسجيل DB. الملفات المؤقتة المرفوضة تنظف، والأصول المقبولة لا تحذف.

أهم الملفات: ingestion/files.py وdatabase/store.py وapplication/service.py وarchiving/files.py. اختبارات التخزين الخمس نجحت، بالإضافة إلى اختبارات القراءة السابقة. شرط الانتقال تحقق لمسار الحفظ، مع بقاء قيد مراجعة OCR.

## المرحلة الرابعة: التصنيف والاستخراج والتحقق

قواعد معلنة للفئتين وغير المعروف، ومطابقة حقول ذات تسميات مثبتة، مع raw/normalized/source/status. تعارض قيمتين لا يحسم، والغياب لا يخمّن. التحقق من التاريخ لا يفترض التقويم؛ الميلادي يتحقق تقويميًا والهجري يبقى للمراجعة، والعملات محدودة بقائمة صريحة، والمبالغ Decimal لا float.

أهم الملفات: classification/rules.py وextraction/rules.py وvalidation/fields.py. اختبارات الوحدات السلبية والموجبة والمراجعات والمقاييس نجحت. التصحيح لا يعدل نتيجة المحرك، ويعاد فحص الحقول بعد تعديل النص، حتى عند الرجوع إلى نص سابق. كل فشل تقييم أدناه مفصول عن نجاح اختبارات التخزين.

## المرحلة الخامسة: الواجهة والبحث والمراجعة

API محلي وواجهة RTL بنفس العملية، دون Streamlit أو خدمة واجهة أخرى لتقليل العمليات والاعتماديات. أصول HTML/CSS/JS محلية ولا CDN أو خطوط ويب. معاينة PNG مشتقة محليًا من الأصل وتتاح الأصول للتنزيل كما حفظت. الواجهة تدعم رفعًا ثم قراءة ثم مراجعة وتصحيحًا وبحثًا واسترجاعًا، مع فلاتر النوع والحالة وتاريخ المستند الميلادي المتحقق، وسجل نتائج المحاولات السابقة.

اختبارات API الثلاثة نجحت. فحص Chromium الفعلي نجح: رفع PDF، تصحيح حقل وتقويم، تأكيد المراجعة، بحث بالقيمة المصححة، تنزيل ببصمة مطابقة، معاينة أصل مرسومة فعليًا، وعرض بعرض 390 بكسل دون تجاوز أفقي. صفر أخطاء JavaScript وصفر طلبات HTTP/WebSocket خارج loopback. موارد PDF الداخلية للمتصفح ليست إنترنت؛ أزيل الاعتماد عليها باستبدال العرض بمعاينة PNG المحلية. الدليل في browser-smoke.json؛ الصور محفوظة خارج Git في /workspace/smartgov-artifacts.

## المرحلة السادسة: الاختبارات والتقييم والتشغيل دون شبكة

**70 passed، صفر إخفاق وصفر تخطي** في الاختبار المحجوب النهائي، خلال 8.89 ثانية. يوجد تحذير Deprecation واحد من توافق Starlette/AnyIO، وليس اختبارًا متخطى أو فاشلًا. أوامر scripts/setup_dev.sh أعادت الاختبارات أيضًا: 70 passed في 4.65 ثانية، ونجح pip check في البيئة.

scripts/verify_offline_reading.py يحجب إنشاء المقابس ويشغل الاختبارات ومسار API داخل ASGI والنسخ والاستعادة. سجل strace يتضمن IPC محليًا فقط، ولم يرصد محاولات AF_INET/AF_INET6. هذا ليس قطعًا للشبكة عن الجهاز كله؛ هو حجب ومراقبة للعملية المختبرة، مع فحص المتصفح والتثبيت الجديد المنفصلين. لا اختبارات صفرية أو نتائج وهمية استبدلت محرك OCR الحقيقي.

### التقييم الأول المجمد، قبل تشخيص الخلل

8 مستندات اختبار مستقلة عن التطوير على مستوى المستند وعائلة التنسيق: 3 خطابات و3 فواتير و2 غير معروف. كل البيانات اصطناعية من مؤلف واحد؛ لا استقلال مصادر واقعية. جرى تقييم الاستخراج من المرجع النصي، ومن PDF الرقمي، ومن OCR للصورة كل على حدة. التشابه الكبير والمجموعة الصغيرة لا يبرران تعميم أي رقم.

- التصنيف Macro-F1=1.0 على الأقسام الثلاثة في هذه العينة الصغيرة؛ Precision/Recall ومصفوفة الالتباس محفوظة لكل فئة.
- من النص المرجعي: تطابق القيم لكل الحقول 100%، بما فيها حالات null المتوقعة التي يذكر التقرير عددها منفصلًا.
- في أول PDF رقمي وOCR: **صفر من المستندات المدعومة الستة تطابقت جميع قيم حقولها**. أسقط استخراج النص فواصل القالب، ولم تتعرف قواعد الحقول عليه، فظهرت الحقول غائبة. هذه نتيجة فشل محفوظة في mvp-held-out.json ولم تُحذف أو تُعرض كتقييم نجاح.
- OCR الخام CER=19.68% وWER=39.72%؛ بعد التطبيع CER=18.24% وWER=39.72%. لا تكفي جودة OCR هذه لاعتماد آلي.
- PDF الرقمي الخام CER=4.98% وWER=22.70%؛ المطبع CER=7.55% وWER=22.70%، بسبب سقوط فواصل واختلاف المسافات. ارتفاع CER المطبع هنا مرتبط بتغير طول المرجع والفراغات، لا تحسين مصطنع للنتائج.

### إصلاح تشخيصي ثم فحص انحدار، وليس اختبارًا مستقلًا جديدًا

أضيف قبول محافظ لتسمية حقل مثبتة في بداية السطر يتبعها فراغ تخطيطي دون فاصل، مع حالة needs_review، واختبار تطوير عام بالعربية/الإنجليزية. لأن الخلل شُخص باستخدام الاختبار، فإن إعادة القياس على المجموعة نفسها **ليست تقييمًا مستقلًا**، حتى مع ثبات المراجع والوسوم. نتائجها في mvp-regression.json، وتحتاج النسخة التالية مجموعة اختبار جديدة قبل ادعاء دقة مستقلة.

تطابقت جميع قيم الحقول الرقمية بعد الإصلاح التشخيصي في 6/6 مستندات مدعومة، لكن الحقول المستخرجة من فراغ تخطيطي تبقى needs_review. لم يتحسن اكتمال حقول OCR: 0/6. لا تخفي نسبة null الصحيحة ضعف اكتشاف الحقول: التقرير يذكر expected nulls وTP/FP/FN وExact Match وNEM وF1 لكل حقل. F1 هنا مبني على وجود قيمة صحيحة بالضبط، والقيمة غير الصحيحة تحسب FP وFN، ولا تمثل دقة حالات التحقق أو إثبات التقويم.

الأداء في عملية التقييم التشخيصي: بدء الخدمة وتحميل النموذج 0.167 ثانية، وأقصى معالجة حالة 0.636 ثانية، وذروة RSS بعينات 10ms نحو 173.9 MiB. التخزين التجريبي 753,412 بايت لستة عشر سجلًا (نسختان لكل مستند اختبار)، والأوزان نحو 5.4 MiB. الجهاز Linux x86_64 وPython 3.12.14 و5 وحدات CPU منطقية، OMP_NUM_THREADS=1، دون GPU؛ VRAM غير مقاسة. هذه ليست حدود أداء مضمونة لأجهزة أخرى أو ملفات أصعب.

حدود القبول للنطاق الحالي هي سلامة الأصل، حفظ التاريخ، رفض الفشل كنجاح، ودورة يراجعها الإنسان؛ لا هدف دقة تلقائية ناجح لـ OCR. لا توجد عتبة أداء إنتاجية مثبتة، ومقارنة المحركين لا تزال لازمة قبل تحديد مستهدف دقة آلي موثوق.

## المرحلة السابعة: التغليف والنسخ والاستعادة

حزمة Linux x86_64 / CPython 3.12 تحتوي 20 wheel مع التطبيق، وقائمة --require-hashes، وبيانات ara+eng مثبتة المصدر والبصمة، وأمثلة اصطناعية نجاح/مراجعة/فشل، والأدلة والإشعارات. الحجم نحو 25.5 MB غير مضغوط. لا تضم Paddle ولا Python ولا نظام التشغيل؛ يحتاج الجهاز Python 3.12 وvenv/ensurepip وglibc مناسبين مسبقًا. لم تختبر Windows أو macOS أو تثبيت OS جديد.

**نجح تثبيت نظيف في بيئة افتراضية جديدة** من ملفات الحزمة فقط مع --no-index وحجب المقابس. رصد فحص pip قدرتين لإنشاء مقبس IPv6 عند الاستيراد وحُجبتا؛ لا استدعاء connect/sendto/sendmsg أثناء التثبيت، ولا تنزيل أو اتصال خارجي. لم يُخف هذا التفصيل خلف ادعاء عدم وجود أي syscall للمقابس.

بعد التثبيت شُغلت الوحدة المثبتة من site-packages، لا الكود من checkout، واختبر HTTP loopback الحقيقي: PDF رقمي → تصحيح → اعتماد → بحث → تنزيل ببصمة صحيحة؛ صورة → OCR حقيقي → تصحيح النص والحقول → اعتماد؛ PDF فاسد → فشل مع استرجاع الأصل. ثم أوقفت الخدمة ونسخت الأصول وSQLite بصورة متسقة واستعدتها في مجلد جديد وأعدت الخدمة؛ تطابقت النتائج والمراجعات، ونجح البحث في النسخة المستعادة. حُجبت اتصالات Python الخارجية وفُحص strace الأصلي، دون عناوين خارجية مرصودة. التقرير offline-clean-install.json، وآثار الاختبار خارج Git في /workspace/smartgov-offline-validation-2.

تُرفض استعادة فوق مجلد موجود، وتفحص البصمات والمسارات والروابط والملفات الزائدة والعلاقات. النسخة لا تشفر محتواها ولا تمثل سياسة احتفاظ أو تعافيًا مؤسسيًا. إشعارات تراخيص المكونات مرفقة؛ libjbig المضمن GPL-2-or-later، والتسليم محلي داخلي، وإعادة توزيع ثنائيات لطرف آخر تحتاج استيفاء التزامات الترخيص والمصدر واختيار المالك لترخيص الكود.

## الملفات الرئيسية والخطوة التالية

README ودليل المستخدم والدليل التقني يشرحون التشغيل بالاعتماد على التعليمات فقط. سكربتات التجهيز والتغليف والتقييم والمتصفح والاختبار دون شبكة محفوظة في scripts. الأصل والنماذج وقاعدة البيانات وملفات الحزمة الثنائية خارج Git وفق المتطلبات؛ يحتوي Git على الكود والاختبارات والتوثيق والمراجع الاصطناعية الصغيرة وتقارير القياس.

حُفظ install_script وstart_skill في مسودة إعدادات البيئة، واختُبرت خطوات التجهيز في الجلسة الحالية. هذا ليس نشرًا للبيئة أو تحققًا من استعادتها في مهمة سحابية جديدة. راجع إعدادات البيئة واحفظها ثم انشرها إذا أردت استخدامها في المهام القادمة. إضافة نطاق Paddle السابقة ما زالت في المسودة ولم تُفعّل في الجلسة؛ ليست مطلوبة لدورة MVP الحالية.
